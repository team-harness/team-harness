用户给的是一段观点，不是提纲。这个 skill 的任务是把它变成一篇符合他风格的文章，并且把他每次 review 的意见沉淀回沉淀文件，让下一篇更接近他的品味。

沉淀分四层，各有一个家：

| 文件 | 存什么 | 回答的问题 |
| --- | --- | --- |
| [`voice.md`](voice.md) | 写法规则 | 他会怎么写 |
| [`positions.md`](positions.md) | 已立的判断和术语 | 他已经说过什么 |
| [`bank.md`](bank.md) 素材节 | 经历、数字、坑 | 他手里有什么料 |
| [`bank.md`](bank.md) 选题节 | 值得写的题目 | 接下来写什么 |

**开工前把四个都读完。** 本文件只管流程。

## 1. 先问，别先写

拿到那段话，不要直接开写。用户脑子里有的比写下来的多，缺的部分你猜不出来。

先查 [`bank.md`](bank.md)：这个题目是不是已经在选题里？库里有没有现成素材？有就带着它们去问，问题会具体得多（「上次那个锚点静默失效的事，放这篇合适吗」好过「有没有踩过的坑」）。

然后一次性列出要问的，别挤牙膏。通常缺这几样：

- **这篇要说服谁改变什么看法？** 决定开场从哪个共识切进去。
- **有没有真实的经历、数字、踩过的坑？** 这是文章里最有说服力的材料，也是最容易漏报的——用户往往觉得「那个不值一提」。明确追问。
- **哪些是已经想清楚的判断，哪些还没有？** 两者都要写，但写法不同，混在一起会显得虚。
- **要不要提产品？提哪个？** 不提也完全可以。

问出来的新素材，**这篇用不上的也当场记进 `bank.md`**，不然它就随对话丢了。

完成标准：你能说出这篇的核心判断是什么、支撑它的具体材料有哪些。说不出就继续问。

## 2. 先给骨架

先对照 [`positions.md`](positions.md)：

- 用到已定义的术语（Gate、thin harness、底稿……）就链接到定义处，一句话带过，不整段重讲。
- **新主张和已立的观点矛盾时，不许悄悄绕开或悄悄照写。** 明确问用户：是观点变了，还是这篇的场景不同？变了的话，讨论旧文要不要注记，`positions.md` 也要更新。观点演化是正常的，无声的自相矛盾才是问题。

再扫一眼 `content/posts/` 里已发布的文章：和哪篇有重叠？重叠部分是链接过去，还是这篇换个角度重讲？

然后只给章节标题加每节一句话的意图，不写正文。等确认。

标题按 [`voice.md`](voice.md) 的规则写成判断句或问句。骨架阶段就能看出结构问题，写完再改代价大得多。

顺序上检查一件事：后面的节有没有依赖前面还没交代的概念。有就调序。

## 3. 写正文

按 [`voice.md`](voice.md) 逐条对照着写。写完自己过一遍：

- 每个产品名出现之前，读者已经有那个问题了吗？
- 有没有一处「还没解决」的坦白？全文都是结论会假。
- 收尾落在判断上了吗？

## 4. 交付给用户 review

写进 `content/posts/<slug>.md`，frontmatter 字段规范见仓库 README 的「写一篇新文章」一节。

**先不部署。** 等 review 过一轮再发。

草稿阶段可以加 `draft: true`，这样它不进列表和路由，但可以先提交进 git。

结构上留意一个坑：侧边目录的锚点是按 `##` 出现顺序编号的 `section-1`、`section-2`……**发布后在中间插入一节，会让后面所有锚点后移**，已分享的深链会指错位置。所以定稿前就把结构定下来，发布后补内容尽量往末尾加。

## 5. 吸纳 review 意见 ← 这一步不能省

用户提修改意见时，改文章只是一半。另一半是给每条意见分拣去处——review 里冒出来的不只是写法意见，四层都可能出现：

- **写法意见，换一篇还成立** → [`voice.md`](voice.md)。
  例：「转到 Threadshare 有些突兀」→「产品名出现前先把缺口写出来」。
- **新的判断、立场、术语，或对旧观点的修正** → [`positions.md`](positions.md)。
  例：「我构建 threadshare 的初衷是……人的发问，就是最原始的需求」——这是主张，不是写法。
- **顺嘴讲的经历、数字、坑，这篇用不上的** → [`bank.md`](bank.md) 素材节。
- **「这个其实值得单独写一篇」** → [`bank.md`](bank.md) 选题节，带上是什么触发的。
- **只关于这篇的事实订正**（「六条应该是七条」）→ 只改文章，不记。

记之前先在目标文件里找有没有已覆盖的条目。**有就改写那一条，不要新增**——同一个意思出现两遍，以后改起来会漏。

voice.md 的规则写成两部分：一句祈使句，加这次的「原句 → 改后」。例子比规则本身更能教会人。能用用户的原话就用原话。

记完在回复里用一行告诉他记到哪了，让他有机会说「这条你理解错了」。

单个文件超过 30 条左右时，先合并同类项再加新的。规则堆成一百条就没人（包括你）会真的逐条对照了。

## 6. 部署

review 定稿后：

```bash
npm run build
https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890 npm run deploy
```

代理挂了的话，ClashX 的分组可能选中了失效节点，切到「自动选择」。

验证不要只靠 grep：先确认取回的文件不是空的、也不是 SPA 兜底的 index.html（那个大约 1.3 KB），再比 md5 是否和本地 `dist/` 一致，最后才做文案检查。

发布后收尾三件事：文章用掉的素材在 [`bank.md`](bank.md) 挪进「已用」并标出处；写这篇时立的新判断补进 [`positions.md`](positions.md)（出处就是这篇的 `#section-N`）；选题节里对应的题目划掉。

## 7. 公众号版（可选）

用户要的话，在 `content/wechat/<slug>.md` 出一份。不会发布到站点。

改写规则见 [`voice.md`](voice.md) 末节。改完做一次双向比对，确认每处差异都是有意的，别让站点版的修订漏掉公众号版。
