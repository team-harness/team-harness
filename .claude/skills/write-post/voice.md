# 风格规则

写 team-harness.com 文章时逐条对照。由 [`SKILL.md`](SKILL.md) 第 5 步维护：用户每次 review 提的、换一篇文章还成立的意见，都追加到这里。

标了 **[原话]** 的是用户在 review 里明确说过的，权重最高。其余是我从 `content/posts/intro.md` 提取的，可能提歪了，看到不对直接改。

**这些规则是围栏，不是模板。** 它们说的是「这个作者不会怎么写」，不是「每篇必须怎么写」。如果每篇都以个人经历开场、每个产品段都收在同一个句式、每个结论都用「X 不行 Y 也不行」夹出来，风格就成了套路——读者第二篇就看穿了。同一个句式一篇里最多用两次，跨篇要换着来；拿不准某条规则用不用，宁可不用。

---

## 开场

**开场讲自己的经历或观察，不从命题开始。** 第一段先落地，第二段再转折。

> 我自己全面用 Agent 写代码大约半年，交付确实快了很多，这一点没什么可怀疑的。
>
> 但快的主要是写代码那一段，而且这份快来自模型本身，跟我怎么组织工作没什么关系。

**开场那句共识要真的是共识**，不能是为了转折而立的靶子。

## 论证

**先承认对方的对，再转折。** 不树稻草人。

> 四层各自能单独用，单独补一层也确实有改善。只是它们之间更像相乘而不是相加，最弱的那一层决定整体能到哪。

**用了类比就标出它的边界。** 这是这个作者最有辨识度的动作之一。

> 不过这个类比只成立一半。汇编能被忽略，是因为**编译器的翻译是确定的**。

**用「X 不行，Y 也不行，要的是 Z」把结论夹出来**，比直接给结论有力。

> 给全了不行。完整的上下文人根本看不完……压狠了也不行，压到只剩一句「要不要继续」……要的是刚刚好。

**写自己踩过的坑，包括自家产品的失败。** 这是全文最有说服力的材料，不要因为难看就删。

> 我们让 Agent 按项目实际情况描述 CodeStable，它给出「按需求、架构、特性、问题、审查、决策六个维度组织」。读着顺，也符合直觉；真去翻仓库才发现完全不是。

**明确说出还没解决的部分，用具体的话。** 不要写「仍在探索中」这种糊过去的说法。

> 文字规则仍是这套系统最薄的一环。
>
> 我们做了些实践，也一直在调，但远谈不上有成熟做法。

全篇都是结论会显得假。至少要有一处坦白。

## 产品怎么出现

**产品名出现之前，读者必须已经有那个问题。** 先把缺口写出来，产品才是答案。 **[原话，2026-08-07]**

> 转到 threadshare 是不是有些突兀？

改法是在产品名前面补上缺口那一句：

> 摘要在 gate 现场就给了。底稿还差一个能交出去的形式：完整会话存在发起人的本地工具里，换个人根本打不开。
>
> [Threadshare](...) 把 Agent 对话转成只读链接……

**讲产品讲创始动机和真实场景，不讲抽象好处。** **[原话，2026-08-07]**

> 我构建 threadshare 的初衷是为了解决，人把和 Agent 的结论给别人，别人在不了解双方对不齐的时候，可以去看下和 Agent 的对话。人的发问，就是最原始的需求。

这段口述后来落成正文里最好的一句：

> 人向 Agent 的发问，就是需求最原始的样子。

**产品段落收在「它可以被替换，但这件事不能缺」。** 这个句式反复出现，是刻意的——主张比实现重要。

> Paseo 可以被替换，人和 Agent 都能 Anywhere 这件事不能。
>
> Licell 可以替换，这个接口不能缺。

## 句子和用词

**段落 2–4 句，一段一个意思。**

**用具体数字，不用形容词。** 不写「大幅精简」，写：

> v1 最多有 24 个入口……v2 收敛到 7 个入口，全部 skill 加起来六百行出头。

同类：`高频必读事实不超过 25 条`、`同一个审查阶段最多三轮`。

**小结用短句，落在判断上。**

> 收益是租来的，不是攒下的。
>
> 人是流程里的门。

**加粗只给判断句，和第一次出现的关键术语。** 不加在普通名词上。

> **软件工程二十多年积累的东西没有过时，需要重新编排的是人和 AI 的关系。**
>
> **砍掉的不是工程要求，是对模型每一步怎么做的规定。**

**个人经历用「我」，项目主张用「我们」。**

> 我自己全面用 Agent 写代码大约半年……
>
> 我们的判断相反。Agent 越快，这些东西反而越必要。

**不用的东西**：emoji、感叹号、「赋能」「革命性」「颠覆」「最佳实践」「一站式」，以及任何形容自家产品「强大」「领先」的话。

## 标题

**章节标题写成判断句或问句，不是名词短语。**

> 软件工程没有过时，它换了执行者
>
> 人不看的地方，靠什么兜底
>
> 什么时候不需要这套
>
> 那谁还关心框架

## 格式

- Agent、gate、Harness、token、slug 等英文术语不翻译，直接混排，前后不加空格以外的处理。
- 代码、字段名、命令、文件路径用反引号。
- 表格只在真的是二维信息时用（比如四层对应四个工具），不要拿它排比句。
- 链接直接挂在产品名第一次出现的地方。

## 结尾

**结尾不总结全文，往前推一步，并且承认不确定。**

> 这个位置最终会稳定在哪里，现在没人知道。上一次抽象层下沉用了十几年，这一次大概也不会更快。

## 公众号版

`content/wechat/<slug>.md`，不发布到站点。基于站点版改写：

- 整篇用「我」，包括站点版里写「我们」的地方。
- 段落切得更碎，适应手机阅读。
- 去掉反引号——公众号渲染不好看。
- Team Harness 的介绍方式不同：站点版读者已经在官网上，公众号版要先交代这是什么。
- 开源仓库的入口放在文章讲项目的那一节，不单独放结尾 CTA。

改完做一次双向机械比对（normalize 掉链接语法、加粗、反引号和中文标点后比较段落集合），确认每处差异都是有意的。站点版改了内容，这里很容易漏。
